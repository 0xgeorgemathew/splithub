# SplitHub

SplitHub is a tap-to-pay onchain payments product with three feature pillars:

- `Stores` for merchant checkout, catalog and inventory, and sales analytics
- `Venues` for closed-loop venues: guests top up the venue's credits with USDC and spend them at its stalls
- `Splits` for shared expenses, payment requests, circles, and settlement

The physical tap experience is powered by Arx Halo NFC chips. The chip is an authorization device: it signs
an EIP-712 `PaymentAuth`, and `SplitHubPayments` pulls the funds from the chip owner's wallet (approved
during onboarding). The chip never holds the money and there is no relayer: whichever wallet is signed in on
the device submits the transaction.

## Stack

- **Frontend:** TanStack Start (TanStack Router, file routes in `packages/web/src/routes`) on Vite, React 19, Tailwind CSS 4, DaisyUI 5
- **Hosting:** Cloudflare Workers (`splithub` Worker on `splithub.space`) via `@cloudflare/vite-plugin`, configured in `packages/web/cloudflare.config.ts`
- **Wallet/Auth:** Privy, Wagmi, Viem
- **NFC:** `@arx-research/libhalo`
- **Backend/Data:** Cloudflare D1 (SQLite) behind a supabase-js compatible layer (`lib/db`), Durable Object realtime
- **Contracts:** Foundry, Solidity 0.8.19, OpenZeppelin, Base Sepolia (`84532`)
- **Runtime:** Bun workspaces

## Tap Payments

Every payment surface goes through the same primitive:

- `packages/web/lib/tapPayment.ts`: `PaymentAuth` typed data, chip owner lookup (`SplitHubRegistry.ownerOf`),
  nonce read, and `verifyPaymentTx` (server-side check of the `PaymentExecuted` event)
- `packages/web/hooks/useTapPayment.ts`: one tap when the payer is the signed-in user, two taps on a
  merchant or stall terminal (identify chip owner, then sign); the device wallet submits `executePayment`

Venues use the same tap pattern with `VenueCredits` instead of `SplitHubPayments`: the chip signs a
`CreditPurchase` (top-up) or `CreditSpend`, and the device wallet submits it (`lib/venueCredits.ts`,
`hooks/useVenueCredits.ts`).

Server routes never trust a client-reported payment: they verify the transaction before recording an order or
venue credit activity. Multi-settle collects several chip signatures and submits them in one Multicall3 transaction.

## Routing (TanStack Start)

- Pages: `src/routes/**.tsx` with `createFileRoute(path)({ component })`; dynamic segments use `$param`
  (`src/routes/store/$storeSlug.tsx`). Data that must load on the server uses a `loader` with
  `createServerFn` (see the store and venue routes).
- API: server routes in `src/routes/api/**.ts` with `server: { handlers: { GET, POST } }`, returning `Response`.
- `src/routeTree.gen.ts` is generated by the Vite plugin on `dev`/`build`; commit it with route changes.
- Navigation: `Link to=... params=...`, `useNavigate()`, `useLocation()`, `Route.useParams()` / `useSearch()`.
- Browser-only modules (libhalo NFC, heavy wallet UI) load lazily: `utils/clientOnly.tsx`, dynamic `import()`.
- Public env vars are `VITE_*` (`import.meta.env`); server secrets are Worker bindings read via `process.env`.

## Auth and Ownership

- Client calls that change data use `apiFetch` (`lib/apiFetch.ts`), which sends the Privy access token.
- API routes call `requireUser(request)` (`lib/auth.ts`): it verifies the token against Privy's JWKS and maps
  the Privy user to `users.wallet_address`. Never trust a wallet sent in the request body.
- Venues: any signed-in user can set one up; the owner's wallet registers it on `VenueCredits` first and
  `/api/venues/create` reads the venue id from that transaction. Stalls, edits, pausing and deleting are
  owner-only (`requireVenueOwner`, `services/venueAccess.ts`).
- Stores: the store owner is the wallet that created it (from `requireUser`, never the body). Settings, items
  and stock are owner-only through `requireStoreOwner` (`services/store/storeAccess.ts`).
- Browser writes through `/api/db` need a signed-in caller and pass the ownership rules in `lib/db/policy.ts`
  (rows matched by an update/delete are checked first); users, venues, venue stalls, stores and payments are
  not browser-writable.
- Recording a payment (store order, venue top-up/spend/refund) requires the caller to be the wallet that submitted the
  transaction, mined in the last 30 minutes; settlements and payment-request completion verify the matching
  `PaymentExecuted`. Each payment tx is recorded once (unique indexes, migration 0004).

## Product Surfaces

### 1. Stores

- store setup by any signed-in user: a name and an optional description (slug derived, globally unique)
- the owner manages catalog items (name, price, optional description/image, active/paused) and a stock count,
  and can pause the store, all from the store page
- public store browsing
- tap checkout: one onchain payment from the buyer's wallet to the store owner's wallet
- store analytics: revenue, orders, top items, recent orders, low stock

Primary routes:

- `/store`
- `/store/[storeSlug]`

Primary code:

- `packages/web/src/routes/api/stores`
- `packages/web/services/store`
- `packages/web/components/store`

### 2. Venues

A venue is a closed loop (arcade, festival, resort). Each venue has its own credits on `VenueCredits`:
1 USDC buys 10 credits, credits only work at that venue and cannot be transferred.

- venue setup by any signed-in user (one on-chain `createVenue` from the owner's wallet)
- stalls priced in credits (fixed price, or any amount entered on the terminal)
- top-up terminal (`/venues/$venueSlug/topup`): guest taps twice, USDC moves from their wallet into the venue
- stall terminal: guest taps twice to spend credits
- owner: withdraw the USDC guests have spent (unspent credits stay backed), refund a guest's unspent credits,
  open/close the venue, live activity feed
- guests see their balance on the venue page and enable credits once (USDC approval for `VenueCredits`)

Primary routes:

- `/venues`
- `/venues/[venueSlug]`
- `/venues/[venueSlug]/topup`
- `/venues/[venueSlug]/[stallSlug]`

`/events/*` and `/credits` redirect to `/venues`.

Primary code:

- `packages/web/src/routes/api/venues`
- `packages/web/services/venueService.ts`, `services/venueAccess.ts`
- `packages/web/lib/venueCredits.ts`, `hooks/useVenueCredits.ts`
- `packages/web/components/venues` (terminal in `components/venues/terminal`)

### 3. Splits and Tap Payments

- group expenses
- live balances
- payment requests
- circles and auto-splitting
- settle and multi-settle flows

Primary routes:

- `/splits`
- `/expense/add`
- `/settle`
- `/settle/[requestId]`
- `/multi-settle`
- `/request/create`
- `/requests`

## Contracts

- **SplitHubRegistry**: maps chip addresses to owners
- **SplitHubPayments**: executes chip-signed `PaymentAuth` transfers from the owner's wallet
- **VenueCredits**: closed-loop credits per venue: top up with USDC, spend at stalls, owner withdraws spent USDC
  or refunds unspent credits

## Data Layer

- `supabase` from `~~/lib/supabase` is the D1 client (`lib/db`): same builder API (`from().select().eq()...`,
  embeds like `users!payer_wallet(name)`, `!inner`, `or()`, `upsert`, `single`/`maybeSingle`, `PGRST116`).
- Server code runs plans directly on D1; browser code POSTs plans to `/api/db`, gated by `lib/db/policy.ts`
  (reads open, writes only for the tables/actions client code performs).
- `supabase.channel().on("postgres_changes", ...)` is served by the `RealtimeHub` Durable Object; every write
  through `lib/db` publishes changes.
- Schema changes: add a file under `migrations/`, update `lib/db/schema.ts`, run `bun run web:test` (checks they match).

## Important Flows

### Store checkout

1. Build a server-side quote for the cart.
2. The buyer taps their chip; the device wallet submits one `executePayment` to the store owner's wallet.
3. The checkout route verifies the `PaymentExecuted` event against the quote (submitter is the caller, mined in
   the last 30 minutes, tx not recorded before).
4. Persist the order and its items, and decrement stock.

Relevant files:

- `packages/web/src/routes/api/stores/$storeId/checkout.ts`
- `packages/web/services/store/storeCheckout.ts`
- `packages/web/components/store/StoreCheckoutClient.tsx`

### Venue top-up and spend

1. The guest taps their chip on the venue terminal (identify, then sign a `CreditPurchase` or `CreditSpend`).
2. The terminal wallet submits it to `VenueCredits` (top-up pulls USDC from the guest; spend burns credits).
3. `/api/venues/activity` reads the mined event (submitter is the caller, last 30 minutes, once per tx) and
   records it; top-ups also run circle auto-split.

Relevant files:

- `packages/web/hooks/useVenueCredits.ts`
- `packages/web/components/venues/terminal/VenueTerminal.tsx`
- `packages/web/src/routes/api/venues/activity.ts`

## Product Constraints

- Treat `Stores`, `Venues`, and `Splits` as the product's features.
- Do not describe the app as only bill splitting.
- The chip is an authorization device, not a stored-value vault. Funds stay in the user's wallet until payment.
- Do not add a relayer or server-held signing keys for payments; the user's tap plus a device wallet is enough.
